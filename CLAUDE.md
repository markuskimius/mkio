# mkio

Config-driven Python microservice framework. Single TCP port serves HTTP + WebSocket, backed by embedded SQLite.

## Build & Test

```bash
pip install -e ".[dev]"        # Install with dev dependencies
pip install -e ".[fast,dev]"   # With orjson + uvloop acceleration
pytest tests/                  # Run all tests
pytest tests/ -x -v            # Stop on first failure, verbose
python scripts/gen_expr_docs.py   # Regenerate README expression-function tables from the registry (tests check they're in sync)
```

## Architecture

```
src/mkio/
├── __init__.py       # Public API: serve, create_app, MkioApp, init, get_default_config, Service, ChangeEvent, expr, register_function/library/type
├── app.py            # MkioApp class + create_app() factory — programmatic server lifecycle
├── auth.py           # Password hashing (bcrypt/PBKDF2), RightsCache, access checking, when SQL pre-checks
├── scaffold.py       # init() project scaffolding + get_default_config() + template strings
├── _json.py          # orjson-with-fallback (dumps -> bytes, loads)
├── _ref.py           # "YYYYMMDD HH:mm:ss.mmmuuunnnppp" ref strings
├── expr/             # Expression language (see "Expression language" below)
│   ├── __init__.py   # compile / compile_template / compile_filter / compile_formatter, registries, analysis
│   ├── _lexer.py, _parser.py, _ast.py   # tokens → AST (positions kept for error messages)
│   ├── _eval.py      # AST → closures over a Scope chain; Closure (lambda values), Arg (lazy thunks)
│   ├── _env.py       # Env, FunctionDef/TypeDef registries, register_function/library/type
│   ├── _values.py    # pinned semantics: kind, truthy, equals, compare, add, number printing
│   ├── _template.py  # "${...}" template splitting
│   ├── _analysis.py  # field_refs, function_refs, numeric_fields
│   └── _lib_*.py     # standard libraries: core, math, string, format, time, collection
├── history.py        # Versioned tables: version numbering, history schema, undo/redo plans
├── config.py         # TOML/dict loader, normalization, validation
├── migration.py      # Schema diff, change classification, data preservation
├── database.py       # Dual aiosqlite connections (write + read), WAL mode
├── change_bus.py     # Async broadcast with pre-serialized bytes
├── writer.py         # Write batcher: SAVEPOINTs, single commit per batch
├── ws_protocol.py    # JSON envelope helpers
├── server.py         # aiohttp wiring, WS dispatch, static serving, config endpoint, monitor protocol
├── services/
│   ├── base.py       # Service base class with monitor notification
│   ├── info.py       # Built-in _mkio service: server identity and metadata
│   ├── transaction.py # Config-driven SQL ops + result cache
│   ├── subpub.py     # In-memory cache + topic-based single-row push
│   ├── stream.py     # Ring buffer + ref-based cursor
│   ├── query.py      # SQLite snapshot + change feed
│   └── reqrep.py     # One-shot request-reply with SQL/expressions
└── client/
    ├── __init__.py   # Python client with auto-reconnect
    ├── mkio.js       # JS client, auto-served at /mkio.js
    └── mkio-expr.mjs # JS expression language (ES module), auto-served at /mkio-expr.js; same fixtures as mkio/expr
```

## Key Patterns

- **Write path**: TransactionService -> WriteBatcher queue -> batch with SAVEPOINTs -> single COMMIT -> ChangeBus publish -> fan out to subscribers
- **In-memory databases** use shared-cache URI (`file:mkio_{uuid}?mode=memory&cache=shared`) so write and read connections see the same data
- **Expression language** (`mkio.expr`) — one grammar shared with the JS implementation (`client/mkio-expr.mjs`, served at `/mkio-expr.js`), pinned by the conformance fixtures in `tests/expr_cases.json` which both test suites run. Syntax: literals (`42`, `1e6`, `1_000`, quoted strings with the usual escapes plus `\u{..}`; `TRUE FALSE NULL` are the only reserved words), names (case-sensitive; `` `any string` `` in backticks), arrays, maps, `a.b[0]` access, calls `F(x, name: v)` (function names case-insensitive; only registered names and lambda literals are callable), lambdas `x -> body`, pipes `v |> (x -> body)` (right side must be a parenthesized lambda). Precedence low→high: `|>`, `||`, `&&`, `== != < <= > >=` (non-chaining), `??`, `+ -`, `* / // %`, unary `- !` (C precedence), `**`, postfix. Semantics: strict `==` (no coercion); falsy = `NULL FALSE 0 '' [] {}`; one number type, integral values print without a fraction; `//` = `FLOOR(a/b)`, `%` takes the divisor's sign; `&& || ??` and `IF CASE TRY LET` short-circuit; `+` only on number+number or string+string (host types via `register_type`); missing map keys / out-of-range indexes / indexing NULL → NULL; an unknown *root* name is an error in a strict `Env` (mkio's default) and NULL in a lenient one; `__*`, `constructor`, `prototype` keys are blocked. Templates: `compile_template("a ${expr} b")` — a template that is exactly one `${..}` returns the raw value, otherwise a string; `$${` escapes. Standard libraries (all on by default) live in `_lib_core/math/string/format/time/collection.py`; the README's generated tables list every function (`scripts/gen_expr_docs.py`, sync checked by tests) — read the registry, don't restate it here. Time unit is seconds since the epoch; `EPOCH` parses refs and ISO-8601; strftime subset `%Y %m %d %H %M %S %f %z`; tz `UTC`/`local`/`±HH:MM`. `ROUND`/`NUM` round half away from zero on the decimal representation (`ROUND(2.675, 2)` = 2.68). Extension: `register_function(name, fn, lazy=, numeric=, params=, doc=, library=)` (lazy functions get `(ctx, *Arg)` thunks with `.value()`, `.eval(scope)`, `.name`), `register_library(name, {NAME: fn | (fn, meta)})`, `register_type(name, is_instance, add=, to_string=, truthy=, compare=, concat=)` (`concat` joins the type with strings in mixed `${}` templates so it survives; otherwise templates use `to_string`), `Env(libraries=[..], strict=)`. Analysis: `field_refs`, `function_refs`, `numeric_fields` (driven by the `numeric` flag). Parsing is env-free; `compile` validates function names against the env, so unknown functions fail at config load. Nothing UI-specific lives here — mkui registers its own library/type through these hooks.
- **Ref strings** are lexicographically sortable UTC timestamps with sub-nanosecond counter for uniqueness
- **Table seeding** — Tables can specify `seed = "path/to/file.csv"` (or `.json`, `.jsonl`) in their config. Data is loaded only when the table is first created, not on subsequent startups. Path resolution: `/` = absolute, `./` = relative to cwd, otherwise relative to config file. Seed errors (missing file, bad format, unknown columns) are fatal — server refuses to start. On-disk: `seed_table()` runs inside `apply_changes()` after CREATE TABLE; `apply_changes` adds `_mkio_ref` column to newly created tables before seeding so refs can be populated. In-memory: `async_seed_table()` runs in `Database.start()` after `_mkio_ref` column is added. Both validate column names against the table schema. Each seeded row gets its own unique `_mkio_ref` timestamp.
- **Versioned tables — model** — `versioned = true` on a `[tables]` entry gives every row a `_mkio_version` counter (1 on insert, +1 per edit) and records every version in `<table>__history`, keyed `(base pk..., _mkio_version)`. The base row is a **cursor** into that chain: its source columns equal the history row at its own `_mkio_version`; an absent base row means cursor 0. Versions for a key are contiguous 1..N. Writing at version V discards recorded versions >= V, so an edit after an undo drops the abandoned redo branch; `delete` truncates the whole chain (a delete is a real delete). `history.py` owns the naming convention (`HISTORY_SUFFIX = "__history"`, `history_table_name`, `is_history_table`, `base_table_name` — a suffix so a history table sorts next to what it records; only a *trailing* `__history` is reserved), schema derivation (`history_columns` copies source types and strips every constraint; meta columns `_mkio_version _mkio_op _mkio_ref _mkio_user _mkio_service`), `HistorySpec` (insert/truncate/truncate-all SQL), `undo_plan`/`redo_plan` (`VersionPlan`: a primary statement plus an edge-case fallback), and `orphan_history_gc_sql`.
- **Versioned tables — config and capture** — Config load rejects app tables whose name ends in the suffix, versioned tables declaring `_mkio_`-prefixed columns, and versioned tables **without a primary key**; it stores synthetic table configs under `config["_history_tables"]` (underscore key → excluded from `config_hash` and the `_mkio` table list); `effective_tables(config)` merges them for validation, migration and introspection. Services may be configured on a history table by name; transaction ops targeting one are rejected. Capture is **writer-side**, not trigger-based: `WriteBatcher._capture_history` truncates then inserts inside the request's SAVEPOINT, so a rolled-back transaction records nothing and the archiver's own deletes produce no history. Versioned ops maintain the counter in SQL (`VALUES (…, 1)`, `SET _mkio_version = _mkio_version + 1`, upsert via `ON CONFLICT DO UPDATE SET … = t._mkio_version + 1`), use `RETURNING *` + `fetchall()` so multi-row updates version each row independently, and deletes gain `RETURNING *`. History `ChangeEvent`s publish only when `ChangeBus.has_subscribers(hist_table)`. Attribution comes from `ws._mkio_auth` in `TransactionService.on_message` or `MkioApp.execute(user=)`.
- **Versioned tables — undo/redo and maintenance** — `undo`/`redo` are op types (keyed on the full primary key, no `fields`) executed by `WriteBatcher._execute_version_op`, which reads the pre-image via the plan's `current_sql`, then tries the plan's primary statement and its fallback (undo at v1 deletes the row; redo from absent rebuilds v1), raising `nothing to undo/redo` when neither matches. They write no history, and their emitted `ChangeEvent` op is decided at runtime (`emitted` list in `_execute_batch`, which now holds built events), so undo can emit `delete` and redo `insert`. The emitted event carries `cause` (`"undo"`/`"redo"`) and `old` (the pre-image), giving listeners both shapes; `server._on_startup` wires a single ChangeBus listener over all versioned base tables that dispatches these to `MkioApp._undo_redo_hooks`, cancelled in `_on_shutdown` alongside the rights listener. Cross-op `bind` works with them since the plan's returned row lands in `returned_rows`. `baseline` rows backfill existing data at version 1 when versioning is first enabled (`migration.baseline_table` + `add_version_column`, in `apply_changes` after seeding, and in `Database.start()` for `:memory:`). Migration treats history tables as additive-only, never proposes dropping one (`orphan_history_tables()` + `mkio dbupdate --drop-history`), excludes `BASE_INTERNAL_COLUMNS` from diffs, and **carries `_mkio_ref`/`_mkio_version` across a versioned table's recreate** (losing the counter would strand the chain). `mkio dbupdate` discards redo state via `migration.collect_redo_garbage` (orphaned chains + versions above the cursor), reporting counts; `--keep-redo` skips it and server startup never does it. `mkio archive` writes versions older than a ref cutoff to CSV (fsynced before any delete, whole run one transaction, deletes addressed by key+version), **never archiving the version a live row sits on** unless `--prune-source` — which additionally deletes live rows whose entire chain was archived and which still match the newest archived version exactly (`_mkio_version` included).
- **Schema migration** uses recreate-table strategy for changes SQLite's ALTER TABLE can't handle. `mkio serve` refuses to start if schema differs from config (unless `auto_migrate` is set). `mkio dbupdate` applies changes with level control: `--allow-risky` for potentially destructive, `--allow-destructive` for all. `auto_migrate` config accepts `"safe"`, `"risky"`, or `"destructive"` (or `true` → `"safe"`). Service startup errors (e.g., bad SQL) are caught during preflight before the event loop starts, ensuring clean exit.
- **`_mkio_ref` column** is automatically added to all tables by the framework. The writer stamps each row with the transaction's `ref` on INSERT/UPDATE/UPSERT. If the client supplies a `ref`, it is used directly; otherwise the server generates one. Stream services seed their buffer from the DB using this column on startup, enabling cursor-based reconnection across server restarts. Migration system excludes `_mkio_ref` from schema diffs. SubPub and Query services include `_mkio_ref` in every published row (snapshot and update). For SubPub not-found rows, `_mkio_ref` defaults to `null` unless the service config has a `defaults` entry for it. `_mkio_ref` survives formatters (`publish` config) and field projection — it is always set explicitly from the source row after formatting.
- **Op-level `defaults`** in transaction op specs provide static values the client doesn't send (e.g., `defaults = { status = "accepted" }`). Stored in `CompiledOp.defaults`, used by `_extract_params` as fallback when the field isn't in client data.
- **`txnid` echo** — Transaction messages may include an optional `"txnid"` string. The server echoes it back on both result and error responses, letting clients correlate async responses. Not stored in the DB or propagated to subscribers. Supported in CLI CSV/JSON via `_ENVELOPE_KEYS`.
- **`subid` echo** — Subscribe messages may include an optional `"subid"` string. The server echoes it on every outbound message (snapshot, update) for that subscription, letting clients correlate responses when multiplexing subscriptions on a single WebSocket. Stored on the subscriber dataclass, passed through `make_snapshot`/`make_update` via keyword arg. Multiple subscribes to the same service can share a `subid` to form a group (e.g., multiple subpub topics under one subid). The server refcounts subscriptions per service per connection. Unsubscribe with `"subid"` removes only matching subscribers; without `subid` removes all for that connection (backward compatible). `on_unsubscribe` returns the count of subscribers removed.
- **`cause` on live updates** — The `update` envelope (`ws_protocol.make_update(..., cause=)`) carries `"cause": "undo"|"redo"` when the change came from a version cursor move, and omits the key entirely otherwise, so ordinary updates are byte-identical to before. SubPub, Query and Stream all pass `event.cause` through (SubPub via `_notify_topic(..., cause=)`, including its re-query path, factored into `_requery_and_notify`); Query tags its synthesized filter-drop `delete` too. The JS client's `onUpdate` gained a third `info` argument (`{cause, ref, service, subid}`, `cause` null for an ordinary write) — additive, so two-arg handlers still work; the Python client yields whole message dicts so `cause` is already visible; the CLI prints `UPDATE <op> (<cause>)`. Server-side listeners that want the *old* row shape use `MkioApp.on_undo_redo`; the wire deliberately carries only `cause`, since a subscriber already holds the previous row from its snapshot and update stream, and shipping `old` would have to survive formatters and field projection.
- **`_mkio_row` field** — QueryService adds a `_mkio_row` string to every published row (snapshot, update) identifying the row by its primary key(s). PK columns are discovered at startup via `PRAGMA table_info` for all tables in `watch_tables` (primary table first, then secondaries, deduplicating by column name). For single-column PKs the value is `str(pk_value)`; for multiple PK columns it's a compact JSON array (e.g., `["P1",10]`). Collision-free since PK structure is fixed per table set. Always included even when `fields` projection is active.
- **SubPub topic protocol** — SubPub subscribe requires a `"topic"` field (a primary key value, or an array of primary key values for multi-topic subscribe). The server always returns exactly one row in the snapshot with `_mkio_exists: true/false` indicating whether the topic was found. Not-found rows include all output fields with null values (or configured defaults via `defaults = { field = "expression" }` in service config — values are expression strings compiled at startup, e.g., `defaults = { price = "0", label = "'n/a'" }`). Defaults are evaluated per-request with `_mkio_topic` available, so `defaults = { symbol = "_mkio_topic" }` sets the symbol to the subscriber's topic value. Defaults keys are validated at config load time against output columns (publish columns if publish is configured, otherwise table columns). All live changes are sent as `op: "update"` (never "insert" or "delete") — if a topic transitions from not-found to found, it's an update with `_mkio_exists: true`; if deleted, it's an update with `_mkio_exists: false`. Cache keys are stringified for consistent topic matching across integer/text primary keys.
- **`_mkio_topic` field** — SubPub adds `_mkio_topic` to every published row (snapshot, update, found and not-found) identifying the subscriber's topic value. Always included after projection, like `_mkio_exists`. This replaces the previous behavior of injecting the raw topic column (e.g., `topic_key`) into not-found rows, which was inconsistent when a `publish` formatter was active.
- **SubPub `where` filter** — Optional expression filter on cached rows. Rows not matching `where` at startup are excluded from the cache. If a cached row is updated and no longer matches `where`, it is frozen at its last matching state (not evicted, no notification sent). When the row matches again, the cache updates and subscribers are notified normally. This "freeze" semantic means `where` controls entry into the cache but never causes eviction.
- **SubPub `sql` option** — By default SubPub uses `SELECT * FROM primary_table`. Set `sql` to a custom query to compute topics, JOIN tables, or reshape data. The `topic` field must name a column in the query result. When `sql` contains a JOIN, SubPub uses re-query on change events instead of direct cache update.
- **Field projection** — Subscribe messages may include `"fields": ["col1", "col2"]` to receive only the specified columns in each row. Filtering still operates on the full row before projection. Both Query and SubPub preserve all `_mkio_` prefixed fields (`_mkio_row`, `_mkio_ref`, `_mkio_topic`, `_mkio_exists`) through projection. Stored on the subscriber dataclass and applied at output time.
- **Stream pagination** — `"maxcount": N` on a stream subscribe returns at most N rows with `"hasmore"`, and creates **no** live subscription (returns 0). The snapshot `ref` is the last row of the page — the cursor for the next request; once `hasmore` is false, subscribing without maxcount at that ref goes live. Wholly stateless server-side: the ring buffer is the only state. `ref` is optional; omitting it starts from the beginning of the buffer. **Backward**: `"before": true` returns rows *before* the ref (with `maxcount`, the N closest to it), the snapshot `ref` being the earliest row of the page; without `ref` it returns the last N in the buffer. `before` never goes live. Rows are always chronological either way. CLI: `mkio stream <url> <service> --before --ref <ref> --maxcount 20`.
- **Authentication and access control** — Enabled when `_mkio_rights` table exists in `[tables]`. When auth is enabled, all services are locked by default. Each service/op declares `access` in config: `"open"` (no auth), `"auth"` (any logged-in user), `"right_name"` (role must have right), or a dict mapping right names to SQL `when` pre-checks (`{trade_full: true, trade_limited: "accounts WHERE balance >= :qty * :price"}`). The `_mkio_rights` table maps `(role, right)`. The `_mkio_users` table is optional for built-in username/password auth; without it, use `app.on_auth(callback)` for custom auth (JWT, LDAP). Auth protocol: client sends `{"type": "auth", "data": {"username", "password"}}`, server responds `{"type": "auth", "ok": true, "user", "role"}`; the result is stored on the connection as `ws._mkio_auth`. Rights are cached in memory, refreshed via a ChangeBus subscription on `_mkio_rights`. Denial returns a nack for subscribes, an error for transactions. Monitors see auth exchanges under service `_auth`, and denials too (inbound monitored before the access check, the denial as outbound). Clients (JS and Python) store credentials and auto-re-auth on reconnect before re-subscribing. `when` SQL pre-checks run as `SELECT 1 FROM <when> LIMIT 1` binding `:user`, `:role`, `:topic`, submitted data fields, and extra `_mkio_users` columns. Dict-form op shorthand allows `access` alongside `op_type`/`fields`, normalized to list form in `_normalize_service` and stored in `svc["_op_access"]`; op-level access overrides service-level. **Monitor access**: top-level `monitor_access` takes the same values as service `access`. With auth enabled and `monitor_access` unset, monitoring is disabled entirely; denied monitors get an `error`. CLI: `mkio adduser <username> <role>` prompts for password and inserts bcrypt-hashed row. Password hashing uses bcrypt (`pip install mkio[auth]`) with PBKDF2 fallback (per-password random salt, format `pbkdf2:<hex_salt>:<hex_dk>`). `mkio hashpass` generates hashed passwords for seed files. All WS-based CLI commands accept `--username <user>` for authentication; the password is read from the `MKIO_PASSWORD` environment variable, or prompted interactively if not set. `mkio adduser` and `mkio hashpass` also read `MKIO_PASSWORD` when set.
- **Query pagination** — `"maxcount": N` on a query subscribe sends at most N rows per snapshot with `"hasmore"` (present on every snapshot, false when unpaginated). Without a `subid` the server auto-assigns one (prefixed `_mkio_q_`); the client pages with `{"type": "getmore", "service", "subid"}`. Updates arriving mid-pagination are buffered and burst-delivered after the final page, capped at `max(configured_max_buffer, snapshot_size + maxcount)` so at least one page of updates fits. On overflow the subscriber is kept with an `overflowed` flag and the next `getmore` is nacked (`"subscription reset: update buffer overflow"`). Paginating subscribers idle for 60s are cleaned up.

## Public API

The `mkio` package exports a stable programmatic API for embedding mkio in other Python applications. These are the public symbols in `__init__.py`:

- **`serve(config)`** — Blocking entry point. Takes `str | Path | dict`. Delegates to `create_app(config).run()`.
- **`create_app(config, *, routes=None) -> MkioApp`** — Factory that loads config and returns a controllable server handle. `routes` is an optional list of `(method, path, handler)` tuples for custom HTTP endpoints.
- **`MkioApp`** — Server lifecycle wrapper. Methods grouped by category:
  - *Pre-start registration* (raise `RuntimeError` if already running):
    - `add_routes(routes)` — Add HTTP routes before starting.
    - `add_service(name, cls, config=None)` — Register a custom `Service` subclass. Instantiated during `start()` with the same lifecycle as config-driven services (monitors, WS dispatch all work). `config` defaults to `{}`.
  - *Lifecycle hooks* (append-only callback lists, multiple callbacks called in order):
    - `on_startup(callback)` — Async callback invoked after all services start.
    - `on_shutdown(callback)` — Async callback invoked before services stop.
    - `on_connect(callback)` — Async callback `(ws) -> None` invoked when a WebSocket client connects.
    - `on_disconnect(callback)` — Async callback `(ws) -> None` invoked when a WebSocket client disconnects.
    - `on_undo_redo(callback)` — Async callback `(ChangeEvent) -> None` invoked after every undo/redo on a versioned table. Raises `RuntimeError` if already running (the listener is wired at startup). The event carries `cause` (`"undo"`/`"redo"`), `old` (row before, `None` if absent) and `new` (row after, `None` if removed), so the application can diff the two shapes to derive its dependent action. Hooks run post-commit and may write through `execute()`; one that raises is logged and does not stop the others.
    - `on_auth(callback)` — Register a custom async auth handler `(data: dict) -> dict` that overrides table-backed auth. Must return `{"user": str, "role": str, ...}`. Raise to reject.
  - *Data facade* (raise `RuntimeError` if server not running):
    - `async execute(service, data, *, op=None, user=None) -> {"ok": True, "ref": "..."}` — Submit a transaction through the normal write path (WriteBatcher → ChangeBus → subscribers). Same semantics as a WS client. Raises `KeyError` for unknown service, `ValueError` for non-transaction service or unknown op.
    - `async query(sql, params=()) -> list[dict]` — Read query on the read connection via `Database.read()`.
    - `async history(table, *, pk=None, since=None, until=None, limit=1000, newest_first=False) -> list[dict]` — Recorded versions of a versioned table, ordered by key then `_mkio_version` (the history table name is accepted too). Raises `ValueError` if the table is not versioned.
    - `async subscribe(tables, callback) -> unsub_fn` — Subscribe to `ChangeEvent`s on the given tables. `callback` is `async (ChangeEvent) -> None`. Returns an unsubscribe function that cancels the drain task and removes the ChangeBus subscription.
  - *Server lifecycle*:
    - `async start()` — Non-blocking server start (binds port, begins serving).
    - `async stop()` — Graceful shutdown (drains writes, closes connections, checkpoints DB). Idempotent.
    - `async wait()` — Blocks until `stop()` is called or a signal is received.
    - `run()` — Blocking convenience: `asyncio.run(start + wait)` with signal handling and optional uvloop.
  - *Properties*:
    - `.config` — The resolved config dict (always available).
    - `.db` — `Database` instance. `None` before `start()` / after `stop()`. **Unstable API.**
    - `.writer` — `WriteBatcher` instance. `None` before `start()` / after `stop()`. **Unstable API.**
    - `.change_bus` — `ChangeBus` instance. `None` before `start()` / after `stop()`. **Unstable API.**
    - `.services` — `dict[str, Service]` map. Empty before `start()` / after `stop()`. **Unstable API.**
- **`ChangeEvent`** — Dataclass for change bus events: `table`, `op`, `row`, `ref`, `raw_bytes`, plus `cause`/`old` (set only by an undo/redo cursor move) and the `new` property (`None` when `op == "delete"`, else `row`). Used as the callback argument for `MkioApp.subscribe()` and `MkioApp.on_undo_redo()`.
- **`history_table(name) -> str`** — Name of the history table recording versions of a versioned table (`<name>__history`). Also re-exported from `mkio.client`; the JS client exposes `historyTable(name)` / `mkio.historyTable(...)`.
- **`init(directory, *, no_static=False) -> list[Path]`** — Scaffold project files (server.toml, static/index.html). Raises `FileExistsError` if server.toml already exists.
- **`get_default_config() -> dict`** — Returns the scaffold template config as a Python dict (includes static section). Callers can modify before passing to `create_app()`.
- **`Service`** — Base class for custom service protocols. Constructor receives `(config, db, change_bus, writer)`. Override `start()`, `stop()`, `on_subscribe()`, `on_unsubscribe()`, `on_message()`.
- **`register_function(name, fn, ...)`**, **`register_library`**, **`register_type`**, **`expr`** — Expression language extension points and the `mkio.expr` module (see Key Patterns).

**Stability**: From mkio 1.0, exports follow semver — no removal or signature-breaking changes within a major version. New keyword arguments and new exports are allowed in minor versions. Properties marked **Unstable API** (`.db`, `.writer`, `.change_bus`, `.services`) are not covered by semver guarantees — their internal types may change. The data facade (`execute`, `query`, `subscribe`) is the stable interface for the same operations.

**Implementation**: `app.py` contains `MkioApp` and `create_app()`. `scaffold.py` contains `init()`, `get_default_config()`, and the template strings. `server.py` retains the internal aiohttp handlers (`_on_startup`, `_on_shutdown`, `_ws_handler`, etc.) imported by `app.py`. Pending services and lifecycle hooks are stored on `MkioApp` and consumed by `server.py` via `app["mkio_app"]`.

## Conventions

- Python 3.11+ required (for `asyncio.TaskGroup`, `tomllib`)
- All async tests use `pytest-asyncio` with `asyncio_mode = "auto"`
- `from mkio._json import dumps, loads` everywhere (never raw json/orjson)
- Services communicate changes via `ChangeBus` (never direct DB polling)
- **Subscribe protocol** — All subscribe messages require a `"protocol"` field (`"subpub"`, `"stream"`, or `"query"`) matching the service's configured protocol; mismatches, missing values, or unknown services return a `{"type": "nack", "service": "...", "message": "..."}` response (with `ref`, `txnid`, `subid` echoed if present). SubPub requires `topic` (primary key value or array of values) and sends a snapshot with one row per topic + updates. Query supports `snapshot`/`updates` booleans and optional `filter` expressions with `filterable` config. Stream supports optional `ref` for cursor-based reconnection (omit to start from beginning of buffer) and optional `before` boolean to reverse direction (rows before ref instead of after). All subscribe types support optional `fields` list and `subid`. The CLI exits on nack. Both Python and JS clients remove nacked subscriptions from their internal maps to prevent reconnect from retrying rejected subscriptions. The JS client supports an `onNack` callback in subscribe options.
- **ReqRep protocol** — One-shot request-reply. Client sends `{"type": "request", "service": "...", "reqid": "...", "data": {...}}`, server replies with `{"type": "reply", "service": "...", "reqid": "...", ...}`. The `reqid` field is echoed for client-side correlation. Reply shape is determined by config: `reply` as string → `"value"` (scalar), `reply` as dict (no SQL) → `"row"` (single record), `sql` without `reply` → `"rows"` (result set), `sql` with `reply` dict → `"rows"` (each transformed), `sql` with `reply` string → `"value"` (scalar from first row). Optional `params` config (dict of expressions) computes SQL parameters from request data. At least one of `sql` or `reply` is required. Subscribe attempts to reqrep services are nacked. ReqRepService uses `on_message()` (not `on_subscribe`), same dispatch path as transactions.
- **Monitor protocol**: WS clients send `{"type": "monitor", "service": "..."}` to tap into a specific service, or `{"type": "monitor"}` (no service) to monitor all services. Server responds with `monitor_ack`. Nack responses for protocol mismatch/missing protocol are forwarded to monitors. When auth is enabled, monitoring is disabled unless `monitor_access` is configured; denied monitors receive an `error` response.
- **Built-in `_mkio` service** — Auto-registered reqrep service for connection identity, version compatibility, and table schema introspection. Client sends `{"type": "request", "service": "_mkio", "reqid": "..."}` and receives a reply with `row` containing: `name` (config `name`, default `""`), `version` (config `version`, default `""`), `mkio` (framework version), `protocol` (protocol version, semver string, currently `"1.2"`), `expr` (expression language version, exact-match in compatibility checks), `services` (map of service name → protocol, excluding internal `_`-prefixed services), `tables` (list of table names, history tables excluded), `versioned` (base tables recorded to a history table), `history_suffix` (`"__history"`, so the convention is discoverable at runtime), `config_hash` (8-char hex SHA-256 of normalized config), `uptime` (seconds since startup), `started` (ref string of startup time). Optionally accepts `data` with expected versions (`version`, `protocol`, `mkio`, `expr` — any combination). When present, the reply includes `compatible` (bool, AND of all checks) and `compatibility` (dict mapping each requested key to `true`/`false`). Compatibility uses semver caret convention: same major, server >= client; for 0.x, same minor; for 0.0.x, exact match. Unparseable versions (empty, `"dev"`) → `false`; when no expectations are sent, neither field appears. **Schema query**: `data` with a `"table"` key returns that table's schema instead — `table` plus `columns` (`{name, type, notnull, pk, dflt_value}` from `PRAGMA table_info`), with `versioned`/`history_table` on a versioned base table and `history_of` on a history table. History tables resolve (via `effective_tables`) but are omitted from the available-tables list in errors; unknown tables error with that list. Hidden from `/api/services`, service detail API, and error hints. Rejects subscriptions with nack. Access: `_check_service_access` lets `_mkio` through unconditionally and the service gates itself — with auth enabled and no `ws._mkio_auth`, the reply is identity + compatibility only (`services`, `tables`, `versioned`, `config_hash`, `uptime`, `started` stripped; schema queries → `authentication required`); any authenticated user gets everything. Denial errors for `request` messages carry `reqid` and `service` (`make_error(..., reqid=, service=)`) — a request error without `reqid` would leave `MkioClient.request()` pending forever; both clients additionally settle the oldest pending request on an error with no `ref`/`reqid` (older servers). Config supports optional top-level `name` and `version` keys for application identity.
- **Protocol mismatch errors** — Sending `type: "request"` to a non-reqrep service returns an error identifying the service's actual protocol (previously silently ignored). Subscribe protocol mismatches already returned nacks. CLI and browser console display hints suggesting the correct command/method on mismatch.
- **Config endpoint** — `[config]` section maps routes to directories (like `[static]`). Requesting `*.json` first looks for a `*.toml` file, parses it, and returns JSON; if no `.toml` exists, falls back to a literal `.json` file. Other extensions are served as-is. Subdirectories supported. Path traversal blocked. Multiple routes supported (e.g., `"/config" = "./configs"`, `"/settings" = "./settings"`).
- **Service discovery**: `GET /api/services` lists services, `GET /api/services/<name>` returns detailed usage info (fields, types, examples).
- **CLI tools**: `mkio services <url> [service]` lists/inspects services, `mkio send` sends transactions, `mkio subpub`/`mkio stream`/`mkio query` subscribe to live data (each with protocol-specific options), `mkio reqrep <url> <service> [data]` sends a request-reply (data as JSON or key=value pairs), `mkio schema <url> <table>` shows table schema (columns, types, keys, defaults), `mkio check <url> [version=... protocol=... mkio=...]` checks version compatibility with a server (exits 0 if compatible, 1 if not), `mkio dbupdate [config.toml] [--allow-risky] [--allow-destructive] [--drop-history]` applies pending schema migrations (`--drop-history` removes history tables whose base table is no longer versioned), `mkio archive [config.toml] [--table <name>] --older-than <N>d|<ref> [--out <dir>] [--delete] [--prune-source] [--dry-run] [--yes]` archives versioned-table history to CSV, `mkio init [directory] [--no-static]` scaffolds a new project (`--no-static` skips `static/index.html` and the `[static]` config section), `mkio monitor <url> [service] [--filter <expr>]` taps traffic (all services if service omitted), `mkio adduser <username> <role> [config.toml]` adds a user to `_mkio_users` (prompts for password, bcrypt-hashes), `mkio hashpass` generates hashed passwords for seed files. All WS-based CLI commands (`monitor`, `send`, `subpub`, `stream`, `query`, `reqrep`, `schema`, `check`) accept `--username <user>` for authentication; the password is read from `MKIO_PASSWORD` env var or prompted interactively. URL defaults to `localhost`, `http://`, and port 80 — a bare port number like `8080` becomes `http://localhost:8080`
- **Browser console** — The `mkio` object in DevTools mirrors the CLI: `mkio.subpub(service, topic, opts)`, `mkio.stream(service, opts)`, `mkio.query(service, opts)` with protocol-specific options (`snapshotOnly`/`updateOnly` for query, auto-ref for stream), `mkio.reqrep(service, data, opts)` for request-reply, `mkio.schema(table)` for table schema introspection, `mkio.check({version, protocol, mkio})` for version compatibility checking. `mkio.monitor({filter: fn | "expr"})` supports client-side filter functions or expression strings (needs `/mkio-expr.js` loaded as a module; `mkio.expr` exposes it). All subscribe methods return `MkioSubscription` with `.stop()` and provide default `onNack`/`onDelta` handlers. `mkio.services()` fetches and formats the full service list from the server API. Console commands auto-generate `subid`/`txnid`/`reqid` with a `_mkio_` prefix to avoid intercepting application messages.
- **Config validation** — Table/column references, required fields, bind indices, op types, and filterable fields are validated at config load time. Unknown keys produce warnings with typo suggestions. Runtime errors include context (available services/ops/fields).
- **CLI error handling** — All CLI commands catch predictable errors (connection refused, port in use, invalid TOML, invalid config) and show clean one-line messages with hints. Unexpected exceptions still produce tracebacks for debugging. `--traceback` flag or `MKIO_TRACEBACK=1` env var re-raises caught exceptions. Error handling lives in `__main__.py` only (`_serve_error` for serve, `_run_client_command` for client commands, `_connection_error` for connection failures) — `server.py` and `config.py` raise normally.
